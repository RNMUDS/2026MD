第4回で「みんなで動ける空間」＝データを生む装置を作った。でもあの空間、データはどこにも残っていなかった。動いた瞬間に相手へ転送して、それきり。第5回は、その動きをデータベース（SQLite）に1行ずつ記録し、CSVで取り出して pandas で分析する。第3回で他人のCSV（サッカー）を可視化した手つきを、今度は自分たちが生んだCSVに向ける。

📌 第5回の位置づけ：なぜ「記録」するのか（はじめに読もう）

テーマは引き続き 「バーチャル空間で、データサイエンスを実践する」。第4回で作った空間は、たしかにデータを生んでいた。でも、そのデータは流れて消えていた。第5回では、それを残して・取り出して・分析できる形に整える。ここを越えると、ようやく「実験」ができる。

今日の合言葉：「記録されなかったデータは、無かったことになる」

  • 第4回＝動きを相手に転送した。届いたら役目は終わり ＝ データは流れて消える

なぜ「記録」が要るのか ― 消えるデータと、残るデータ

第4回のコードを思い出す：データはどこにも残っていない

第4回の server.js は、こう書いてあった。受け取って、転送して、おしまい。どこにも「書き留める」処理がない。

JavaScript ── 第4回の server.js（一部）socket.on('move', (data) => {
  // 受け取った位置を、そのまま他の人へ転送するだけ
  socket.broadcast.emit('moved', { id: socket.id, position: data.position });
  // ← ここで data は用済み。次の move が来たら上書きされて消える
});

つまり第4回の空間は、「今この瞬間」しか存在しない空間だった。授業が終わってサーバを止めた瞬間、誰がどこを歩いたかはすべて消える。これでは「あの人はどう動いたか」をあとから調べられない＝分析ができない。

メモリ（変数）は「机の上」。作業中はすぐ手が届いて速いけれど、帰るときに全部片付けられてしまう。ファイルやデータベースは「棚」。しまうのに一手間かかるが、明日も来週も、そこに残っている。今日は、机の上の作業を棚にしまう方法を学ぶ。

今日の道具：SQLite（better-sqlite3）

  • SQLite：ファイル1つ（例 logs.db）がまるごとデータベースになる、軽量なしくみ。別途サーバを立てる必要がない
  • better-sqlite3：その SQLite を Node.js から使うための部品。npm install で入る
  • SQL：データベースに「表を作れ」「1行足せ」「全部出せ」と伝えるための言葉。今日は3つだけ覚える

  • だから今日足すコードは、ほとんどが server.js の中。第4回のクライアントはほぼそのまま使える

JavaScript ── server.jsconst express = require('express');
const socketIo = require('socket.io');
const Database = require('better-sqlite3');

const app = express();
app.use(express.static('public'));

const server = app.listen(3000, () => {
  console.log('サーバ起動: http://localhost:3000');
});

const io = socketIo(server);

// データベースを開く（無ければ logs.db が作られる）
const db = new Database('logs.db');

// ログを溜める表を作る（1行 = 行動データ1件）
db.exec(`
  CREATE TABLE IF NOT EXISTS logs (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id TEXT,
    t       INTEGER,
    event   TEXT,
    x       REAL,
    y       REAL,
    z       REAL
  )
`);

// 1行を書き込む命令を、あらかじめ用意しておく
const insertLog = db.prepare(
  'INSERT INTO logs (user_id, t, event, x, y, z) VALUES (?, ?, ?, ?, ?, ?)'
);

io.on('connection', (socket) => {
  console.log('接続しました:', socket.id);
  insertLog.run(socket.id, Date.now(), 'join', 0, 0, 0);

  socket.on('move', (data) => {
    insertLog.run(socket.id, Date.now(), 'move',
      data.position.x, data.position.y, data.position.z);
    socket.broadcast.emit('moved', {
      id: socket.id, position: data.position, color: data.color
    });
  });

  socket.on('click', (data) => {
    insertLog.run(socket.id, Date.now(), 'click',
      data.position.x, data.position.y, data.position.z);
    console.log('クリック:', socket.id);
  });

  socket.on('disconnect', () => {
    console.log('切断しました:', socket.id);
    insertLog.run(socket.id, Date.now(), 'leave', 0, 0, 0);
    io.emit('userLeft', socket.id);
  });
});

// ログを CSV にして返す
app.get('/log.csv', (req, res) => {
  const rows = db.prepare('SELECT * FROM logs ORDER BY id').all();
  let csv = 'id,user_id,t,event,x,y,z\n';
  for (const r of rows) {
    csv += `${r.id},${r.user_id},${r.t},${r.event},${r.x},${r.y},${r.z}\n`;
  }
  res.setHeader('Content-Type', 'text/csv; charset=utf-8');
  res.setHeader('Content-Disposition', 'attachment; filename="log.csv"');
  res.send(csv);
});

// ダッシュボード用の集計を返す
app.get('/api/stats', (req, res) => {
  const total = db.prepare('SELECT COUNT(*) AS n FROM logs').get().n;
  const users = db.prepare('SELECT COUNT(DISTINCT user_id) AS n FROM logs').get().n;
  const perUser = db.prepare(
    'SELECT user_id, COUNT(*) AS n FROM logs GROUP BY user_id ORDER BY n DESC'
  ).all();
  res.json({ total, users, perUser });
});

動かないときのチェック

  • 箱がクリックできない：<a-cursor> を <a-camera> の中に書いたか確認する。画面中央の照準を箱に合わせてからクリックする

  • 行数が増えない：3D空間の窓を開いたままにしているか確認する（閉じると move の送信も止まる）

グループワーク gw5：「データはどこを通って、どこに残るか」を説明ラリーで確認する

コードは書かない。さっき動かしたアプリで、データがどこを通って、最後にどこへ残るのかを、声に出してお互いに説明し合うワーク。2〜3人組で行う。

進め方（説明ラリー）

  • 下の確認項目を、1人1つずつ順番に声に出して説明する（1人 → 次の人 → …とラリー）
  • 詰まったら「節1のデータの旅の図」を見てOK。見ずに言えたら◎
  • チーム全員が最後まで言えたらクリア

確認する項目（この内容を口頭で説明できるか）

#口頭で確認すること（例）
1ログが残るのはサーバ側の logs.db。ブラウザ側には残らない（ブラウザは送るだけ）
2表 logs の1行 ＝ 行動データ1件。列は user_id（誰が）・t（いつ）・event（何を）・x,y,z（どこで）
3CREATE TABLE は表の設計図。IF NOT EXISTS が付いているので、2回目以降の起動では作り直さない（＝前のデータが残る）
4INSERT は socket.on の中で呼ぶ。イベントが起きた、まさにその瞬間に1行書く
5move は 100ミリ秒ごとに送られる ＝ 1人あたり毎秒10行ずつ増えていく
6/log.csv は、SELECT で取り出した結果をカンマ区切りの文字に並べ直したもの
7analyze.py（pandas）はサーバとは別のプログラム。CSVを読むだけで、3D空間とは直接つながっていない

言えたらもう一歩：役割で整理してみよう

ブラウザ＝「起きたことを送る」／サーバ＝「受け取って、その場で1行書く」／データベース＝「ためる」／CSV＝「持ち出す」／pandas＝「読んで数える」。この5つの役割を自分の言葉で言えれば、標準課題はスムーズに進む。

Notion に、自分が説明を担当した項目と、詰まった点／すっきり分かった点を1〜2行メモする（gw5）。
3

ログ1行を設計して、表（テーブル）を作る

いちばん大事な設計：1行に「何を」書くか

データ分析でいちばん効くのは、実は最初の1行の設計。ここを間違えると、あとで何を計算しようとしても足りない。逆にここさえ押さえれば、分析は驚くほど楽になる。合言葉は「誰が・いつ・何を・どこで」。

問い列（カラム）意味・例
誰がuser_id第4回で出てきた socket.id。接続ごとに自動で振られる背番号
いつtDate.now() の値。1970年から数えたミリ秒（例 1784118015584）
何をeventjoin（入室）／move（移動）／click（クリック）／leave（退室）
どこでx y zそのときのカメラ（＝その人）の位置
防犯カメラの記録を思い浮かべよう。「誰が・何時何分に・何をして・どこにいたか」が揃っていれば、あとから何度でも再現・検証できる。1つでも欠けると「この動きは誰のもの？」「これは何時の話？」となって使えなくなる。ログ設計とは、未来の自分への申し送りである。

用語：データベースの言葉（第2回・第3回とつながっている）

言葉意味これまでの言い方
データベース表をまとめて保管する入れもの（＝logs.db ファイル）―
テーブル（表）同じ形のデータを並べたもの（＝logs）CSVファイル1枚（第3回）
カラム（列）項目（＝user_id, t, …）CSVの見出し行
レコード（行）データ1件（＝行動データ1件）オブジェクト {x, y, z}（第2回）
主キー1行を見分けるための番号（＝id）―

つまり「テーブル」は、第3回で読んだCSVと同じもの。置き場所がファイルかデータベースかが違うだけ。だから最後に SELECT して並べれば、そのままCSVに戻せる。

分解：いま書いた「SQL」を読み解く

SQL は「データベースへの命令文」。今日は3つだけ覚える

SQL は、データベースに用事を伝えるための言葉。世界中のデータベースでほぼ共通で、データサイエンスの現場で最も使われる道具のひとつ。種類はたくさんあるが、今日使うのは3つだけ。

SQL意味今日の使いどころ
CREATE TABLE表を作る（設計図）起動時に1回だけ。列の名前と型を決める
INSERT INTO1行足すsocket.on の中で、イベントが起きるたびに
SELECT取り出す/log.csv と /api/stats で、溜めたものを読む

読み解き①：CREATE TABLE IF NOT EXISTS logs ( … )

部分意味
CREATE TABLE表を作れ
IF NOT EXISTSもし無ければ（すでにあれば何もしない）
logs表の名前
user_id TEXTuser_id という列を作る。中身は文字
t INTEGERt 列。中身は整数
x REALx 列。中身は小数（位置は 1.6 のような小数になる）
id INTEGER PRIMARY KEY AUTOINCREMENT1行ごとに1, 2, 3… と自動で番号を振る。主キー（行の見分け札）

なぜ IF NOT EXISTS が要るのか：サーバは何度も起動する。毎回まっさらな表を作り直したら、前回のログが消えてしまう。「無ければ作る、あればそのまま使う」＝データが積み上がっていく。今日の「再起動しても消えない」は、この3語のおかげ。

読み解き②：prepare と run、そして ? の意味

JavaScript// ① 命令の「型」を1回だけ用意する（? は、あとで値を入れる場所）
const insertLog = db.prepare(
  'INSERT INTO logs (user_id, t, event, x, y, z) VALUES (?, ?, ?, ?, ?, ?)'
);

// ② 実際の値を入れて実行する（何度でも使い回せる）
insertLog.run('aB3xK9', 1784118015584, 'move', 0, 1.6, 4);
  • prepare＝命令の型を先に作っておく。? は「ここに値が入ります」という空欄
  • run＝空欄を埋めて実行する。? の並び順どおりに値を渡す
  • 速い：型は1回作るだけ。move は毎秒10回×人数ぶん来るので、この差が効く
  • 安全：値を文字列としてつなげて書くと、変な値が入ったとき命令文が壊れる（SQLインジェクションという有名な脆弱性）。? を使えば、値はあくまで値として扱われる

やってはいけない書き方

JavaScript ── 悪い例（マネしない）// 値を直接つなげて命令文を組み立てる
db.exec(`INSERT INTO logs (user_id) VALUES ('${userName}')`);
// userName に変な文字が入ると、命令文そのものが書き換わってしまう

必ず prepare ＋ ? を使う。これは実務でもいちばん基本的で、いちばん重要な作法。

読み解き③：SELECT の3つの形（/api/stats で使っている）

SQL意味
SELECT * FROM logs ORDER BY id全部の列（*）を、id の順に並べて取り出す
SELECT COUNT(*) AS n FROM logs行数を数えて、n という名前で返す
SELECT user_id, COUNT(*) AS n FROM logs GROUP BY user_iduser_id ごとにまとめて数える

GROUP BY＝「〜ごとにまとめて集計する」。この考え方は、このあと pandas の groupby でそっくりそのまま出てくる。SQL と pandas は、同じことを別の言葉で書いているだけ。

動きとクリックを記録する

標準課題 std5-2：move と click を1行ずつ書き留める

表ができたので、いよいよ本命のデータを溜める。ポイントは「イベントが起きた、まさにその瞬間に1行書く」こと。①〜④を埋める。

① server.js ── io.on('connection', …) の中（背景色が追記部分）

JavaScript ── server.jsio.on('connection', (socket) => {
  console.log('接続しました:', socket.id);
  insertLog.run(socket.id, Date.now(), 'join', 0, 0, 0);

  // 誰かが動いたら「記録してから」転送する
  socket.on('move', (data) => {
    insertLog.run(socket.id, Date.①(), 'move',
      data.position.x, data.position.y, data.position.z);
    socket.broadcast.emit('moved', {
      id: socket.id, position: data.position, color: data.color
    });
  });

  // 誰かが箱をクリックしたら、その瞬間の位置を記録する
  socket.on('②', (data) => {
    insertLog.run(socket.id, Date.now(), 'click',
      data.position.x, data.position.y, data.position.z);
    console.log('クリック:', socket.id);
  });

  socket.on('disconnect', () => {
    console.log('切断しました:', socket.id);
    // 退室も記録する（滞在時間を出すのに使う）
    insertLog.run(socket.id, Date.now(), '③', 0, 0, 0);
    io.emit('userLeft', socket.id);
  });
});

考えてみよう：move の行だけ、やけに多いのはなぜ？

join・click・leave は人が起こしたときだけ1行。でも move は setInterval で100ミリ秒ごとに自動で送られるので、1人あたり毎秒10行増える。2人が10秒いるだけで約200行。この「取る細かさ」＝サンプリング間隔が、あとの分析の精度と重さを決める（節7でもう一度考える）。

CSV で取り出す ― データベースから、分析の世界へ

なぜ CSV に直すのか

ログは logs.db に溜まった。でもこのファイルは Node.js（JavaScript）の世界の住人。一方、分析の主役 pandas は Python の世界にいる。この2つの世界をつなぐ共通語が CSV。

CSV は「翻訳された書類」。JavaScript も Python も Excel も R も、CSV なら読める。だからデータサイエンスの現場では、まず CSV に落として渡す場面がとても多い。第3回で読んだサッカーのデータも、誰かがどこかのデータベースから CSV に落としてくれたもの。

ここで一周する

第3回：誰かが用意した soccer.csv を pd.read_csv で読んだ。今日：その「誰か」を自分たちがやる。CSVを作る側に回ると、データがどう生まれるのかが 体で分かる。

標準課題 std5-3：/log.csv で取り出せるようにする

server.js のいちばん下に書き足す。SELECT で全部の行を取り出し、カンマ区切りの文字に並べ直して返すだけ。①〜③を埋める。

📁 編集するファイル：server.js（いちばん下に追加）

JavaScript ── server.js の末尾に追加// ログを CSV にして返す
app.get('/log.csv', (req, res) => {
  // ① 全部の行を id 順に取り出す
  const rows = db.prepare('① * FROM logs ORDER BY id').all();

  // ② 1行目は見出し（列の名前）
  let csv = 'id,user_id,t,event,x,y,z\n';

  // ③ 1行ずつ、カンマでつないで足していく
  for (const r of rows) {
    csv += `${r.id},${r.user_id},${r.t},${r.②},${r.x},${r.y},${r.z}\n`;
  }

  res.setHeader('Content-Type', 'text/csv; charset=utf-8');
  res.setHeader('Content-Disposition', 'attachment; filename="log.csv"');
  res.send(csv);
});

// ダッシュボード用の集計を返す
app.get('/api/stats', (req, res) => {
  const total = db.prepare('SELECT COUNT(*) AS n FROM logs').get().n;
  const users = db.prepare('SELECT COUNT(DISTINCT user_id) AS n FROM logs').get().n;
  // user_id ごとにまとめて数える
  const perUser = db.prepare(
    'SELECT user_id, COUNT(*) AS n FROM logs ③ user_id ORDER BY n DESC'
  ).all();
  res.json({ total, users, perUser });
});

穴埋めのヒント

  • ①：「取り出す」SQL（節4の3つのうちのひとつ）
  • ②：見出しの並び id,user_id,t,event,x,y,z と同じ順番になるように、4番目の列名を入れる
  • ③：「〜ごとにまとめる」＝2語（英語）

覚えておくと得：\n と「見出し行」

  • \n＝改行。CSVは「1行＝1レコード」なので、1行足すごとに \n で改行する
  • 1行目の見出しが、そのまま pandas の列名になる。ここを揃えておくと df['user_id'] のように書ける
  • Content-Disposition: attachment＝ブラウザに「表示せずダウンロードして」と伝える指定

7

pandas で前処理して、軌跡を可視化する（標準ゴール）

生のログは、そのままでは分析できない

CSVは手に入った。でも中身を見ると、そのままでは使えない行がたくさん混ざっている。分析の前に整える作業を前処理という。実務では、分析にかける時間の半分以上が前処理とも言われる。今日は代表的な3つをやる。

前処理やることなぜ必要か
単位をそろえるミリ秒 → 経過秒1784118015584 のままでは人間が読めない。0秒から数え直すと扱いやすい
いらない行を落とすevent == 'move' だけ残すjoin／leave の行は位置が 0,0,0。混ぜると軌跡が原点に飛ぶ
重複を落とす同じ場所の連続を1件に止まっていても100msごとに記録される。移動距離の計算では邪魔

「いらない行を落とす」を忘れると、どうなるか

join と leave の行は、位置を 0, 0, 0 で記録している（入室した瞬間は、まだどこにいるか分からないため）。これを混ぜたまま軌跡を描くと、線が毎回わざわざ原点(0,0)に飛んで戻るという、実際には起きていない動きが描かれてしまう。「そのデータは何を意味する行なのか」を考えずに全部使うと、平気で嘘のグラフができる。これは前処理を学ぶ最大の理由。

標準課題 std5-4：analyze.py で集計して、軌跡を描く（標準ゴール）

md2_no5 の直下に analyze.py を作る（log.csv と同じ場所）。①〜④を埋める。第3回で使った pandas・matplotlib がそのまま登場する。

md2_no5/ ├── server.js ├── logs.db ├── log.csv ← ダウンロードしたCSVをここに置く ├── analyze.py ← これを作る └── public/
Python ── analyze.pyimport pandas as pd
import numpy as np
import matplotlib.pyplot as plt

# --- 1. 読み込む ---
df = pd.read_csv('log.csv')
print('=== 生データ ===')
print(df.head())
print('行数:', len(df))

# --- 2. 前処理 ---
# 時刻をミリ秒 → 秒（0からの経過秒）に直す
df['sec'] = (df['t'] - df['t'].min()) / 1000

# 移動ログだけを取り出す（join / leave / click を除く）
move = df[df['event'] == '①'].copy()

# 同じ場所に止まっている重複行を除く
move = move.drop_duplicates(subset=['user_id', 'x', 'z'])

print('\n=== 前処理後 ===')
print('move の行数:', len(move))

# --- 3. ユーザごとに集計する ---
rows = []
for user_id, g in move.②('user_id'):
    g = g.sort_values('sec')
    # 1歩ぶんの差を出して、三平方の定理で距離にする
    dx = g['x'].diff()
    dz = g['z'].diff()
    distance = np.sqrt(dx**2 + dz**2).sum()
    duration = g['sec'].max() - g['sec'].min()
    clicks = len(df[(df['user_id'] == user_id) & (df['event'] == 'click')])
    rows.append({
        'user_id': user_id[:8],
        '移動距離': round(distance, 2),
        '滞在時間': round(duration, 1),
        'クリック回数': clicks,
    })

summary = pd.DataFrame(rows)
print('\n=== ユーザごとの集計 ===')
print(summary.to_string(index=False))

# --- 4. 軌跡を描く ---
plt.figure(figsize=(6, 6))
for user_id, g in move.groupby('user_id'):
    g = g.sort_values('sec')
    # 真上から見た図なので、横軸 x・縦軸 z（y は高さなので使わない）
    plt.plot(g['x'], g[③], marker='o', markersize=3, label=user_id[:8])
plt.xlabel('x')
plt.ylabel('z')
plt.title('Movement trajectory')
plt.legend()
plt.grid(alpha=0.3)
plt.axis('equal')
plt.savefig('④', dpi=120, bbox_inches='tight')
print('\ntrajectory.png を保存しました')

穴埋めのヒント

  • ①：移動を表すイベント名
  • ②：「〜ごとにまとめる」pandas のメソッド。SQL の GROUP BY と同じ働き（節4を思い出す）
  • ③：真上から見た地図なので、縦軸には奥行きの列を使う（y は高さなので違う）
  • ④：保存するファイル名。最後の print と揃える

発展課題 ― 記録のしくみを、自分の興味に向ける

発展課題 adv5-1：アイデアを1つ以上選んで、自分の空間を「もっと語るデータ」にする（任意）

標準ゴールまで来たら、「自分は何を知りたいか」を考えてみよう。知りたいことが決まると、取るべきデータも決まる。下から1つ以上選んで挑戦する（AIに聞きながらでOK。大事なのは作れるかではなく説明できるか）。

A. 取るデータを増やす

アイデア①：「どの箱を」クリックしたかを記録する

いまは「クリックした」ことしか分からない。どの箱かが分かれば、人気の箱ランキングや選択率が出せる。表に target 列を足すところから始める。

JavaScript ── public/index.html（送る側）<a-box class="target" id="box-orange" position="-3 1 -5" color="#FF8A3D"></a-box>

// クリックされた箱の id もいっしょに送る
socket.emit('click', {
  position: { x: pos.x, y: pos.y, z: pos.z },
  target: box.getAttribute('id')   // ← 追加
});

※ server.js 側では CREATE TABLE に target TEXT を足し、INSERT の ? を1つ増やす。すでに logs.db がある場合は、いったんファイルを削除してから起動すると新しい形の表が作られる（IF NOT EXISTS があるので、古い表のままだと列は増えない）。

アイデア②：向き（どこを見ていたか）を記録する

位置だけでは「そこで何を見ていたか」は分からない。カメラの回転を足すと、視線の向きが分かる。rx, ry, rz の3列を足してみよう。

JavaScript ── public/index.htmlconst rot = cam.object3D.rotation;
socket.emit('move', {
  position: { x: pos.x, y: pos.y, z: pos.z },
  rotation: { x: rot.x, y: rot.y, z: rot.z },   // ← 追加
  color: myColor
});

アイデア③：サンプリング間隔を変えて、データ量を比べる

setInterval の 100 を 1000（毎秒1回）や 33（毎秒30回）に変えて、同じ1分間で行数がどう変わるか／軌跡の見た目がどう変わるかを比べる。粗いと動きがカクカクになり、細かいと行数が爆発する。このトレードオフを自分の目で確かめるのは、とても良い実験。

B. 見せ方・使い方を育てる

アイデア④：ダッシュボードを育てる

/api/stats に SELECT を足すだけで、いろいろ分かる。SQL を1行足す → 画面に出すのくり返し。

JavaScript ── server.js の /api/stats に足す例// イベントの種類ごとの件数
const byEvent = db.prepare(
  'SELECT event, COUNT(*) AS n FROM logs GROUP BY event'
).all();

// クリックが多い人ランキング
const clickRank = db.prepare(
  "SELECT user_id, COUNT(*) AS n FROM logs WHERE event = 'click' GROUP BY user_id ORDER BY n DESC"
).all();

アイデア⑤：🔥 取ったログを、3D空間で「再生」する

今日いちばんの目玉。第3回では、サッカーの座標CSVを読んでスフィアを動かした。まったく同じ手法で、自分たちの log.csv を再生できる。つまり「さっきの自分の動きを、あとから空間の中で見る」ということ。第3回と第5回が、ここでつながる。

JavaScript ── 再生の考え方（第3回の setInterval と同じ形）// log.csv を読んで、user_id ごとの座標リストにしておく
// （fetch('/log.csv') で取ってきて、行ごとに split(',') で分ける）

let i = 0;
setInterval(() => {
  // i 番目の位置にゴーストを動かす（100ms ごと ＝ 記録したときと同じ速さ）
  ghost.setAttribute('position', path[i]);
  i++;
  if (i >= path.length) i = 0;   // 最後まで行ったら最初に戻る
}, 100);

なぜ 100ms ごとに動かすと、同じ速さで再生できるのか

記録したとき setInterval(…, 100) で100msごとに1行書いた。だから1行 ＝ 100ms。再生も100msごとに1行ずつ進めれば、実際と同じ速さになる。50 にすれば2倍速、200 にすればスローモーション。サンプリング間隔を知っていると、時間を操作できる。

アイデア⑥：Three.js をのぞいてみる

今日ずっと書いていた cam.object3D.position の object3D は、実は Three.js（A-Frameの土台になっているライブラリ）のオブジェクト。A-Frame は Three.js をHTMLタグで書けるように包んだもの。console.log(cam.object3D) をブラウザの Console で実行して、中に何が入っているか（position・rotation・matrix…）をのぞいてみよう。位置データが最終的に「行列」として扱われていることが見える。

データを扱うときの注意

  • 個人が特定できる情報は記録しない。socket.id のようなその場限りのIDにとどめる。名前を記録する場合はニックネームにする
  • 他の人のログを扱うときは、本人に「記録している」と伝える。これは実験の基本的な礼儀であり、ルール（インフォームド・コンセント）
  • logs.db や log.csv をそのままネットに公開しない（授業の提出はOK）

次回への予告：この記録装置で「実験」をする

今日つくったのは測定器。次回はこれを使って実験をする。空間の条件をA / B の2種類つくり、どちらが使いやすいかを、行動データ（移動距離・時間）と主観評価（アンケート）の両方で比べる。そして「この差は、偶然ではないと言えるか？」を統計的検定で判断する。今日の groupby が、次回の主役になる。
