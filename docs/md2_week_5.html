なぜ「記録」が要るのか ― 消えるデータと、残るデータ

第4回の空間を思い出す：データはどこにも残っていない

第4回のサーバがしていた仕事は、たった2つだけだった。受け取って、そのまま転送する。絵にすると、こうなる。

大事なのは、図の下半分だ。サーバは位置を他の人へ渡した瞬間に、その位置を忘れてしまう。書き留める場所（ファイルやデータベース）がどこにもないので、次の位置が届けば上書きされ、前の位置は跡形もなくなる。90分の授業で何万回と動いても、残るのは「今この瞬間」の1件だけ。

だから第4回の空間は、「今この瞬間」しか存在しない空間だった。サーバを止めれば、誰がどこを歩いたかはすべて消える。「あの人はどう動いたか」をあとから調べられない＝分析ができない、ということ。第5回でやるのは、この図に「書き留める矢印」を1本足すことだ。

ファイル1: server.js（md2_no5 の直下）── そのままコピペ

第4回の server.js に、データベースを開く・表を作る・1行ずつ書き込むを足しただけ。ここでは「溜める」だけ。CSVで取り出すのは節4で、そちらはコードを書かずボタン1つでできる。

JavaScript ── server.jsconst express = require('express');
const socketIo = require('socket.io');
const Database = require('better-sqlite3');

const app = express();
app.use(express.static('public'));

const server = app.listen(3000, () => {
  console.log('サーバ起動: http://localhost:3000');
});

const io = socketIo(server);

// データベースを開く（無ければ logs.db が作られる）
const db = new Database('logs.db');

// ログを溜める表を作る（1行 = 行動データ1件）
db.exec(`
  CREATE TABLE IF NOT EXISTS logs (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id TEXT,
    t       INTEGER,
    event   TEXT,
    x       REAL,
    y       REAL,
    z       REAL
  )
`);

// 1行を書き込む命令を、あらかじめ用意しておく
const insertLog = db.prepare(
  'INSERT INTO logs (user_id, t, event, x, y, z) VALUES (?, ?, ?, ?, ?, ?)'
);

io.on('connection', (socket) => {
  console.log('接続しました:', socket.id);
  insertLog.run(socket.id, Date.now(), 'join', 0, 0, 0);

  // 動いたら「記録してから」転送する
  socket.on('move', (data) => {
    insertLog.run(socket.id, Date.now(), 'move',
      data.position.x, data.position.y, data.position.z);
    socket.broadcast.emit('moved', { id: socket.id, position: data.position });
  });

  socket.on('disconnect', () => {
    console.log('切断しました:', socket.id);
    insertLog.run(socket.id, Date.now(), 'leave', 0, 0, 0);
    io.emit('userLeft', socket.id);
  });
});

標準課題コインを置いて、取った回数を記録する

まず「当たり判定」のしくみを知る ― コインに触れた、をどう判定するか

いまの空間は歩くだけで、記録されるのも位置だけ。ここにコインを置いて、「近づいたら取れる」ようにする。すると logs.db に「誰が・いつ・どこで・コインを取ったか」が溜まり、人によって差が出るデータになる。

ここで必要なのが 当たり判定。コンピュータは「触れた」を自動では教えてくれない。自分と相手の距離を計算して、近ければ「当たった」ことにするだけ。使うのは三平方の定理ひとつ。

この式、どこかで見た ― 第3回・そして節5とつながる

  • 当たり判定＝いまの自分とコインの距離 → 近いかを見る
  • 移動距離の集計（節5・pandas）＝いまの自分と1つ前の自分の距離 → 全部たす
  • どちらも √(dx² + dz²)。同じ道具を、ゲームの中と分析の両方で使っている

なぜ「1m」なのか ― これも設計

この 1 は自分で決める数字。大きくすると遠くからでも取れて簡単になり、小さくするとぴったり乗らないと取れず難しくなる。あとで変えて試すとよい。「どこからを『触れた』と呼ぶか」を決めるのは人間で、これも立派なデータ設計。

標準課題CSV で取り出して、pandas で分析する（標準ゴール）

なぜ CSV に直すのか

ログは logs.db に溜まった。でもこのファイルは Node.js（JavaScript）の世界の住人。一方、分析の主役 pandas は Python の世界にいる。この2つの世界をつなぐ共通語が CSV。

CSV は「翻訳された書類」。JavaScript も Python も Excel も R も、CSV なら読める。だからデータサイエンスの現場では、まず CSV に落として渡す場面がとても多い。第3回で読んだサッカーのデータも、誰かがどこかのデータベースから CSV に落としてくれたもの。

ここで一周する

取り出しかた：DB Viewer の Export CSV を押すだけ

CSVへの書き出しは、コードを書かなくてよい。準備で入れた DB Viewer にボタンが付いている。

  • VS Code で logs.db をクリックして開く（サーバは止めてよい）
  • 左の Tables から logs を選ぶ → Refresh で最新にする
  • 上の Export CSV ボタンを押す
  • 保存先を md2_no5 フォルダ、ファイル名を log.csv にする（次の analyze.py がこの名前で読む）

  • md2_no5 の直下に log.csv があるか（analyze.py と同じ場所に置く）
  • VS Code で log.csv をクリックすると、そのまま中身が読める。1行目が見出し（id,user_id,t,event,x,y,z）になっていれば成功
  • 数分歩いただけで数千行になる。それが「行動データ」の量

生のログは、そのままでは分析できない

CSVは手に入った。でも中身を見ると、そのままでは使えない行がたくさん混ざっている。分析の前に整える作業を前処理という。実務では、分析にかける時間の半分以上が前処理とも言われる。今日は代表的な3つをやる。

前処理やることなぜ必要か
単位をそろえるミリ秒 → 経過秒1784118015584 のままでは人間が読めない。0秒から数え直すと扱いやすい
いらない行を落とすevent == 'move' だけ残すjoin／leave の行は位置が 0,0,0。混ぜると軌跡が原点に飛ぶ
重複を落とす同じ場所の連続を1件に止まっていても100msごとに記録される。移動距離の計算では邪魔

「いらない行を落とす」を忘れると、どうなるか

join と leave の行は、位置を 0, 0, 0 で記録している（入室した瞬間は、まだどこにいるか分からないため）。これを混ぜたまま軌跡を描くと、線が毎回わざわざ原点(0,0)に飛んで戻るという、実際には起きていない動きが描かれてしまう。「そのデータは何を意味する行なのか」を考えずに全部使うと、平気で嘘のグラフができる。これは前処理を学ぶ最大の理由。

  • ④：真上から見た図の縦軸。y（高さ）ではない

グラフから読み取ってみよう

  • 右上がりか：点が右上へ並べば「歩けば取れる」。相関係数が +1に近いほどはっきりしている
  • 外れ値はいるか：少ししか歩かずに、たくさん取った人＝ 効率がよい（＝上手い）。左上にポツンといたら、その人の軌跡を見てみる
  • 0枚の人：左下にいるはず。歩いていないのか、歩いたのに取れなかったのか ― 軌跡と見比べると分かる

大事な注意：「関係がある」と「原因である」は別のこと

相関が 0.95 でも、「歩いたからコインが取れた」とは言い切れない。「コインを取りに行ったから、結果として歩いた」のかもしれない。順番が逆の可能性である。データが言えるのは「一緒に増えている」までで、原因を言うには実験が要る ― それが第6回。

Notion に、analyze.py のコード・STEP5とSTEP6の出力・trajectory.png と distance_vs_coins.png を貼り、「歩いた人ほど取れたか」の答えと、グラフから読み取れることを2〜3行で書く（std5-2・標準ゴール）。

おわりに：文法より、考え方 ― AI時代のデータ分析の心得

今日書いた pandas の文法は、AI に聞けば数秒で出てくる。ではもう学ぶことは無いのか ― 逆である。「何を分析するべきか」と「その結果をどう解釈するか」だけは、AI 任せにできない。現場で価値を生むデータサイエンティストは、ライブラリに詳しい人ではなく、「良い問いを立てられる人」。データ分析の標準プロセスとして広く使われる CRISP-DM も、コードではなく「課題を定義すること」を最初のステップに置いている。

AI は優秀な部下。「move の行だけに絞るコードを書いて」と頼めば一瞬で書いてくれる。でも「そもそも何を知りたいのか」だけは、部下からは出てこない。それを決めるのが、あなたの仕事。

① 分析を始める前に ― 問いを立てる

  • 目的を最初に決める：「何を知りたいのか」「何を改善したいのか」を明確にしてから、手を動かす
  • データではなく課題を見る：手元のデータから考え始めない。解決したい課題から考える
  • 良い問いを立てる：「売上は？」ではなく「なぜ売上が下がったのか？」 ― 問いを具体化する
  • 仮説を立ててから分析する：「○○が原因ではないか」という予想を持って、データに向かう

② データに向き合うとき

  • まずデータを疑う：欠損値・外れ値・入力ミス・重複を確認する。今日の join の 0,0,0 が、まさにそれ
  • 平均だけを見ない：分布・ばらつき・中央値・割合も確認する
  • 必ず可視化する：グラフにすると、異常や傾向が一目で分かることが多い
  • データの背景を理解する：誰が・いつ・どのように集めたデータなのか。今日のログは自分たちで集めたから、全部答えられる
  • 比較対象を用意する：前年・平均・他グループ ― 比べて初めて数字は意味を持つ

③ 結果を解釈するとき

  • 相関と因果を混同しない：一緒に動くことと、原因・結果であることは別（さっきの相関 0.95 を思い出す）
  • 分析結果を鵜呑みにしない：他の説明がないか、常に考える

④ 分析を届けるとき

  • 小さく試して改善する：一度で完璧を目指さず、分析→改善を繰り返す。STEP を1つずつ足したのは、この練習
  • 再現できる分析を心掛ける：他の人が同じ結果を得られるようにする。analyze.py は、それ自体が再現できる手順書
  • 結果を相手に伝える：「分かった」で終わらせない。意思決定につながる説明までが分析
  • 倫理を意識する：個人情報・バイアス・公平性。今日の log.csv も人の行動の記録 ― 扱いには責任が伴う
  • AI を部下として使う：コード生成は AI に任せ、人間は目的設定・評価・解釈を担当する

実は、今日の std5-2 はこの心得をなぞっていた

  • 問いを先に立てた ―「たくさん歩いた人ほど、コインを多く取れたのか？」から始めた
  • データを疑った ― STEP1 でまず「見て」、STEP2 で join／leave の行と重複を落とした
  • 数字とグラフの両方で見た ― STEP6 の相関係数だけで終わらず、STEP7 で散布図も描いた
  • 相関と因果を分けた ― 相関 0.95 でも「歩いたから取れた」とは言わなかった

この「見る → 問う → 確かめる → また見る」の繰り返しを探索的データ分析（EDA）と呼ぶ。文法は忘れても、AI に聞けばよい。持ち帰ってほしいのは、この進め方。次回・第6回は、いよいよ「因果」を実験で確かめる。

発展課題 ― インタラクションを増やして、もっと語る空間にする

発展課題 adv5-1：3種類以上のインタラクションを記録できる空間を作る（任意）

いま記録できているのは coin（近づいて取った）の1種類だけ。これを3種類以上に増やし、「その空間で人が何をしたか」がもっと語れるログにする。AIに聞きながらでOK。大事なのは作れるかではなく、「何を知りたくて、その1行を残したのか」を説明できるか。

条件

  • 3種類以上のインタラクションを logs.db に記録すること（event 列で見分けられるようにする）
  • 下の例から選んでも、自分で考えた別のものでもよい
  • やることは今日と同じ形の繰り返し ― ブラウザで気づく → emit で送る → socket.on で受ける → insertLog.run で1行書く。新しく覚えることはない

例①：誰かに近づいた（人と人の距離）

当たり判定の相手をコインから「他の人のアバター」に変えるだけ。誰と誰が近づいたかが分かると、交流のデータになる。

JavaScript ── public/index.html（当たり判定の相手を変える）// コインではなく、他の人のアバター（a-sphere）との距離を測る
document.querySelectorAll('a-sphere').forEach((avatar) => {
  const a = avatar.object3D.position;
  const distance = Math.sqrt((pos.x - a.x)**2 + (pos.z - a.z)**2);
  if (distance < 2) {
    socket.emit('near', { position: { x: pos.x, y: pos.y, z: pos.z }, target: avatar.id });
  }
});

※ そのままだと近づいている間ずっと記録され続ける（毎秒10行）。「離れるまで1回だけ」にするには、いま近くにいる相手を覚えておく工夫が要る ― ここが本当の課題。

例②：何かに近づいた（物への接近・滞在）

看板・展示物・出口などを置き、近づいた＝興味を持ったとみなして記録する。どの展示が人を集めたかが分かる。event は approach など。

JavaScript ── public/index.html<a-box class="exhibit" id="exhibit-A" position="-5 1 -6" color="#4FC3F7"></a-box>

// コインと同じ当たり判定。消さずに、近づいたことだけ記録する
socket.emit('approach', { position: {...}, target: exhibit.getAttribute('id') });

例③：クリックした（意図のはっきりした行動）

近づくのは偶然かもしれないが、クリックは「選んだ」という意図。<a-cursor> を <a-camera> の中に置くと、画面中央の照準でクリックできる。

JavaScript ── public/index.html<a-camera id="cam" position="0 1.6 4">
  <a-cursor color="#FFFFFF"></a-cursor>   // これが無いとクリックできない
</a-camera>

// クリックされた物の id を送る
document.querySelectorAll('.exhibit').forEach((box) => {
  box.addEventListener('click', () => {
    socket.emit('click', { position: {...}, target: box.getAttribute('id') });
  });
});

ほかの案（自分で考えてよい）

  • どこを見ていたか：カメラの回転（cam.object3D.rotation）を move に足す ＝ 視線のデータ
  • 立ち止まった：一定時間ほとんど動かなかったら stay を記録 ＝ 迷い・興味のサイン
  • 入った・出た：ある範囲（部屋・ゾーン）に入った瞬間に enter／exit
  • 走った：1歩の距離がしきい値を超えたら run

ぶつかりやすい壁（ここを越えるのが発展）

  • 同じイベントが大量に記録される：当たり判定は毎秒10回走る。「1回だけ」にする工夫が要る（フラグを持つ／記録したら消す／前回の状態と比べる）
  • target 列を足したい：CREATE TABLE に target TEXT を足し、INSERT の ? を1つ増やす。すでに logs.db があると列は増えない（IF NOT EXISTS のため）ので、いったん logs.db を削除してから起動する
  • どの event 名にするか：あとで df[df['event'] == '___'] で絞るのは自分。読んで分かる名前を付ける

仕上げ：取ったログで、何か1つ言ってみる

Export CSV → analyze.py はそのまま使える。event の名前を変えるだけで、「どの展示がいちばん人を集めたか」「誰と誰がよく近づいたか」が数えられる。グラフを1枚描けたら完成。

Notion に、①記録した3種類以上の event の一覧と「それぞれ何を知りたくて取ったのか」、②実際に3種類が溜まった logs.db のキャプチャ、③書き足したコードを貼る（adv5-1・任意）。
